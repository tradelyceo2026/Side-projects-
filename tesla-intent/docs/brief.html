Design concept v1 · Sept 2026

From commands
to intent

The assistant in the car can now do about 116 things. That is not the problem any more. The problem is that it does not know which 116, it acts without asking, and it forgets what you wanted the moment you stop talking.

A proposal for the in-cabin experience team, with a working prototype.

Where we actually are

The 2026 Summer Update gave the in-car assistant direct control of more than a hundred vehicle functions: glovebox, mirrors, Sentry, wipers, charge port, seat heaters, calls. That was the big unlock, and it shipped. So the obvious pitch, "let the assistant control the car," is already done.

What did not ship is trust. Three gaps survive the update, and all three are design problems rather than capability problems.

It claims things it cannot do

Press coverage of early builds documented the assistant asserting it could adjust seats and climate when it could not. A model that is wrong about its own body is worse than a model with a smaller body, because every correct answer afterward is discounted. This is the single most expensive bug in the experience and it is not fixable by adding more commands.

It is reactive

116 commands still means the driver has to notice the problem, form the sentence, and say it. The car already knows the charge, the route, the outside temperature, the tire that is down four psi and the appointment at three. It should raise the issue before the driver does.

It has no memory of what you want

"Precondition at 7:40" is a command. "Never let me leave for a job under 40 percent" is an intent. Commands expire. Intents should persist and be re-evaluated on every state change. Nothing in the car holds one today.

The assistant does not need more verbs. It needs to know its own limits, to ask before it spends, and to remember what you meant.

The proposal

A layer between natural language and the vehicle bus, built on three rules. The prototype implements all three and you can drive it in a browser.

Grounded capability

Every action is a registered entry: an id, an availability flag, a consent tier, the underlying endpoint, and a reason string when it is unavailable. The model is handed the registry as a tool and is forbidden to describe an action it has not looked up. Ask the prototype to roll down a window and it says the vehicle cannot, names the reason, and states plainly that it changed nothing. That answer is worth more than a hundred that might be true.

Consent proportional to consequence

Comfort applies instantly, because the cost of being wrong is one tap to undo. Anything that spends money, moves the car, or changes security becomes a card with the actual numbers on it and waits for a tap. The assistant is explicit that a card is waiting rather than claiming the thing is done. This is also the cleanest answer to the safety review: the model never silently commits a consequential action.

TierExamplesBehaviour
DirectCabin temperature, seat heaters, volume, lockApplies immediately, one tap to reverse

Standing intents

A sentence that expresses a rule is stored as a rule and re-checked whenever state changes. The prototype ships six anticipation rules driven off live state, and a standing intent the driver sets becomes a seventh. When the charge drops toward a floor the driver declared, the card that appears says which of their own intents is about to be broken. That framing matters: the car is not nagging, it is keeping a promise the driver made.

One surface, three brains, chosen per request. This is the part that answers "how do we get another model in the car" without anyone having to rip anything out.

Getting another model in the car, honestly

Worth being blunt with the team, because the wrong answer here sinks the pitch.

NOT POSSIBLE A native third-party app on the center screen There is no app SDK and no sideloading path. Any proposal that assumes one is dead on arrival.
SHIPS TODAY A web app in the in-car browser The 2026 update added camera and microphone access to the browser on AMD Ryzen cars, which means a real voice loop is possible in-cabin with no firmware change. This is how the prototype would be demoed in an actual vehicle this week.
SHIPS TODAY Fleet API with a virtual key The documented, signed-command path. Registry entries map one to one onto real endpoints such as command/set_temps, command/charge_start and command/set_sentry_mode. The prototype's capability ids were named to match, so swapping the simulator for the real proxy is a single adapter.
THE ACTUAL ASK A first-party pluggable reasoning backend Keep the resident assistant as the voice and personality. Add an interface where a second model can be dispatched to for planning-class work. That is the decision only this team can make, and it is what the prototype exists to argue for.

Objections, answered before they are raised

This is a distraction risk.

It reduces one. Today a driver who wants to change something either says a sentence and hopes, or reaches for the screen. Proposal cards are glanceable, carry the number that matters, and are dismissible with the same gesture as accepting. Anticipated cards appear at rest, not at speed.

Round-tripping to a big model is too slow.

Which is why the router exists. Everything latency-bound stays on-device and never leaves the car. Only planning-class work, where a driver already expects a pause, goes out.

Why not just make the resident assistant better?

Two of the three rules cost nothing and should be done there regardless: ground it in a capability registry and add consent tiers. The routing is separable and can come later. The proposal degrades gracefully.

Liability.

The consent gate is the liability answer. Every consequential action has a recorded driver confirmation against a card that stated the consequence in plain numbers. That audit trail does not exist today.

Nobody asked for standing intents.

Nobody asks for a feature they have never seen. They do complain about arriving somewhere with less charge than they wanted, which is the same thing stated as a symptom.

What to build first

Six weeks, in this order, because each step is useful even if the next one never happens.

  1. The capability registryDeclare every existing command in one schema with availability, tier, endpoint and a reason string. Ship nothing else. This alone fixes the hallucinated-capability problem.
  2. The consent gateClassify those commands into direct, propose and never. Build the card. Instrument the confirm rate.
  3. Three anticipation rulesCold-start preconditioning, range against the queued route, and a tire diverging from the set. Measure whether drivers act on the card.
  4. Standing intentsOne sentence in, one persistent rule out, re-evaluated on state change. Start with charge floors because they are unambiguous.
  5. The routerDispatch by intent class with the on-device path as the default and the fallback.
  6. Work modeJob stops, mileage and invoice lines from vehicle data. The prototype includes it because the author runs a trade business out of a Model Y, and because contractors, realtors and home health are a large, underserved, high-mileage segment that nobody is designing for.

How to tell whether it worked

  • Confirm rate on proposal cards. If drivers tap yes, the car understood the situation. Below 50 percent means the rules are wrong.
  • Corrections per session. Grounded refusals should drive this toward zero.
  • Arrival state of charge versus the driver's declared floor. The number standing intents exist to move.
  • Unprompted resolutions. Problems solved by a card the driver never had to ask for.

Drive the prototype before the meeting. Try "roll down the driver window" to see a grounded refusal, tap a scenario to watch the anticipation rules fire, and set a standing intent, then load the low-charge scenario to watch the car defend it.
